# Zymple v1 spec

Status: draft, nothing built.

"The infra repo" below means the operator's own infrastructure repository:
the Ansible code that configures hosts and holds app definitions and
encrypted secrets. Zymple itself knows nothing about it beyond the files it
renders onto the host.

How this is tested is in [testing.md](testing.md).

## Purpose

Zymple runs applications on a single host. It is a single-host, opinionated deploy tool: an "advanced Dokku" with a
far smaller feature set and attack surface than a general PaaS.

Observability (analytics, errors, traces, uptime) is out of scope. Apps send
telemetry to whatever backend the operator runs elsewhere.

## Principles

1. **No state of its own.** Everything Zymple knows comes from files Ansible
   rendered plus the images in the host's container store. No database, no
   user accounts, no web UI.
2. **No builds on the server.** Images are built with `docker buildx` in CI or
   on a devops machine and pushed to the host.
3. **A deploy names a digest.** Pushing an image does not deploy it. Tags are
   never trusted to stay put.
4. **Opinionated.** docker-compose is the only app format. Postgres and Redis
   are the only managed services. One image per app. One host per app.
5. **Rebuildable.** A host is fully described by the infra repo. Recovery is
   an Ansible run, a Postgres restore, and a re-deploy per app.

## Non-goals for v1

- Building images, buildpacks, preview environments.
- Multi-host apps, clustering, Swarm-style workers.
- Zero downtime across host reboots.
- A web console, teams, roles.
- Managed services other than Postgres and Redis.

## Components

| Piece | What it is | Installed by |
|---|---|---|
| `zymple server` | Go daemon on each app host | Ansible role, pinned version |
| `zymple` CLI | Same binary, used from CI and laptops | Release download |
| Caddy | Host package; TLS and routing | Ansible role |
| Docker | Docker's apt repo, containerd image store enabled | Ansible role |

The server embeds [unregistry](https://github.com/psviderski/unregistry) as a
library, so pushed images land directly in the host's container store. There
is no separate registry process, registry disk, or registry garbage
collection. The stock `docker pussh` SSH flow is not used, because it needs a
root-equivalent SSH credential in CI.

## Network surface

Caddy is the only public listener (80/443). Zymple listens on a loopback port
and a unix socket. Caddy forwards one hostname (`zymple_domain`) to it:

- `/v2/*`: the OCI registry routes.
- `/api/v1/*`: the deploy API.

Web containers publish their port on `127.0.0.1` only. Postgres and Redis
publish nothing; apps reach them over the app's Docker network.

## Authentication

- One token per app, generated once, stored SOPS-encrypted in the infra repo.
  The host holds only its hash.
- The token authorises exactly: push to repository `<app>`, and the deploy API
  for `<app>`. Nothing else, and no other app.
- The registry accepts it as basic auth (`docker login`, user = app name), the
  API as a bearer token.
- Operator commands (restore, shell, logs of any app) are not on the network
  API. They run on the host over SSH, through the unix socket.

## App definition

Lives in the infra repo and is rendered by Ansible to `/etc/zymple/apps/<app>/`.

```yaml
name: myapp
domains: [app.example.com]
compose: compose.yml          # services reference ${IMAGE}
web:
  service: web
  port: 3000
  healthcheck: /healthz
  health_timeout: 60s
  drain: 30s
release: ["bin/migrate"]      # optional, runs before the switch
keep_releases: 5
postgres: { version: 17, pitr_days: 14 }
redis: { persistent: false }
env: secrets/apps/myapp.env   # SOPS
```

Rules:

- Every service in the compose file runs `${IMAGE}`. Zymple substitutes the
  pinned digest.
- Exactly one service is the web service. Only it gets blue/green.
- Other services (job workers, schedulers) are restarted on the new digest
  after the switch.
- Zymple injects `DATABASE_URL` and `REDIS_URL` when those services are
  declared.
- Compose features that break the model are rejected at load time: `build:`,
  published ports, host networking, privileged mode, bind mounts outside the
  app's data directory.

## Host layout

```
/etc/zymple/zymple.yml              server config
/etc/zymple/apps/<app>/             app.yml, compose.yml, env, token hash
/etc/caddy/zymple/<app>.caddy       generated by Zymple
/var/lib/zymple/apps/<app>/         releases.json, volumes, postgres data
```

`releases.json` is the only file Zymple writes as state. It can be rebuilt
from the container store and is not needed for recovery.

## Deploy

```
zymple deploy <app> --image <ref> [--host <host>]
```

1. The CLI pushes the image to `https://<zymple_domain>/v2/<app>` using the
   standard protocol. Layers the host already has are skipped.
2. The CLI calls `POST /api/v1/apps/<app>/deploys` with the digest. The
   response is a stream of events until the deploy ends. The CLI prints them
   and exits non-zero on failure.

Server side, per deploy:

| Step | Action | On failure |
|---|---|---|
| 1 | Check the digest exists in repository `<app>` | Reject |
| 2 | Take the app's deploy lock | Reject: deploy in progress |
| 3 | Run `release` in a one-off container | Abort, old release untouched |
| 4 | Start the new web container on a free loopback port | Abort, remove it |
| 5 | Poll the health check until `health_timeout` | Abort, remove it |
| 6 | Rewrite the Caddy snippet, graceful reload | Abort, restore snippet |
| 7 | Wait `drain`, stop the old web container | Log, continue |
| 8 | Restart the other compose services on the new digest | Report as degraded |
| 9 | Record the release, pin its image, prune beyond `keep_releases` | Log |

Until step 6 succeeds the old release serves all traffic. If the client
disconnects, the deploy continues; `zymple status <app>` reports the result.

## Releases and rollback

- Each successful deploy is a numbered release: digest, time, token id.
- The last `keep_releases` images are pinned by a local tag so Docker's
  pruning cannot remove them. Older ones are unpinned and removed.
- `zymple releases <app>` lists them.
- `zymple rollback <app> [release]` runs the same sequence onto an image that
  is already on the host, skipping the `release` command. No transfer.
- Rollback reverts the image only. Migrations must stay compatible with the
  previous release (expand, deploy, contract).

## Postgres

- One cluster per app, so each app has independent versions and PITR. Each
  cluster is a container managed by Zymple, with its data under
  `/var/lib/zymple/apps/<app>/postgres`.
- The image is `zymple-postgres:<major>`: the official Postgres image plus
  pgBackRest from the PGDG apt repo. The Zymple repository builds and
  publishes it, and each Zymple release pins the image digests it uses, so a
  Postgres minor update arrives with a Zymple upgrade.
- pgBackRest runs inside that container (the archive command needs it there)
  and ships base backups and WAL to an S3-compatible bucket, one stanza per
  app. Bucket and credentials come from the server config.
- The Zymple server schedules backups: full weekly, differential daily,
  retention from `pitr_days`.
- A deploy never restarts the Postgres container. It restarts only when its
  image or settings change, during `zymple reload`.
- Operator commands, on the host:
  - `zymple pg info <app>`: backup set, WAL range, last archive time.
  - `zymple pg backup <app>`
  - `zymple pg restore <app> [--time <ts>] [--into <new-app>]`
  - `zymple pg psql <app>`
- A restore stops the app's services, restores, and starts them again.
  `--into` restores beside the live cluster for drills.
- A major version upgrade is a documented manual procedure in v1.

## Redis

- `persistent: false`: cache only, no volume, no backup.
- `persistent: true`: AOF on a volume, snapshotted to the bucket with restic.

## CLI summary

From CI or a laptop, with the app token:

```
zymple deploy <app> --image <ref>
zymple rollback <app> [release]
zymple releases <app>
zymple status <app>
zymple logs <app> [service]
```

On the host, over SSH:

```
zymple apps
zymple run <app> -- <command>
zymple pg info|backup|restore|psql <app>
zymple reload                  # re-read /etc/zymple after an Ansible run
```

## What the infra repo provides

- A `zymple` role: binary at a pinned version, systemd unit, server config,
  containerd image store enabled in Docker.
- A `caddy` role: package, base Caddyfile importing `/etc/caddy/zymple/*`.
- App definitions and SOPS-encrypted env files and tokens.
- Recipes for deploy-token creation and restore drills.

App deploys run from CI with the app token. Host configuration is
applied by the operator with Ansible.

## Security model

- Zymple holds the Docker and containerd sockets, so it is root-equivalent.
  Its network input is limited to registry pushes and three API calls, all
  behind a per-app token.
- A leaked app token can push images to that app and deploy them. It cannot
  read secrets, reach other apps, or run commands on the host.
- App secrets exist only in the infra repo (encrypted) and on the host's disk.
- Compose validation stops an app definition from escaping its sandbox; app
  definitions are reviewed in the infra repo in any case.

## Risks and open questions

1. **Embedding unregistry is unproven.** It was made importable in v0.3.1, but
   the API has not been read and token auth in front of it is untested. It is
   a young project (v0.4.x). Fallback: embed the stock `distribution` registry
   with local storage, accepting that images are stored twice.
2. **The Postgres image is ours to maintain.** `zymple-postgres` has to be
   rebuilt for every Postgres minor release and pgBackRest update. Chosen
   over host-level clusters so that versions are per app and
   restore is a Zymple command. A Postgres image or settings change restarts
   the database, which is a short outage for that app.
3. **Long release commands.** A migration longer than CI's job timeout needs
   a detached mode; v1 only reports the outcome through `zymple status`.

## Milestones

| | Scope | Done when |
|---|---|---|
| M0 | Spike: embedded unregistry behind token auth | `docker push` with a scoped token lands an image in the host store |
| M1 | Deploy of a web-only app with blue/green | A load test sees no failed requests across a deploy |
| M2 | Compose services, `release`, releases and rollback | Rollback to release n-3 works without a transfer |
| M3 | Postgres with pgBackRest, Redis | A PITR drill restores into a second cluster |
| M4 | Ansible role, first production app | A wiped host is rebuilt from the infra repo alone |
